# F-031: Fundaciones de cuentas por cobrar — modelo de datos y lógica pura

> Escrito por el agente `spec`. **Solo lo esencial que otros agentes necesiten.**
> Sin diseño técnico ni pseudocódigo (eso es del arquitecto), y sin decisiones de UI, layout
> ni responsive (eso es del `ui-designer`, en `.agents/designs/F-031.md` — este feature no toca
> ninguna pantalla, así que no aplica).

## Qué hay que lograr

Sentar las bases de datos y la lógica pura del epic de cuentas por cobrar (ventas a crédito), sin
tocar todavía ninguna pantalla ni ruta de venta. Al terminar deben existir: las tres tablas nuevas
(`Cliente`, `CuentaPorCobrar`, `MovimientoCuentaPorCobrar`) y las columnas aditivas en `Venta`,
`CierrePeriodo` y `MovimientoStock`; los schemas Zod correspondientes; las funciones puras de
saldo, antigüedad, reparto de devolución e invariante del crédito; y el endurecimiento de los dos
agregadores de caja que hoy tragarían en silencio cualquier línea de pago que no sea `cash` ni
`transfer`.

**Lectura obligatoria antes de implementar:** `.agents/cuentas-por-cobrar.md` (dosier del epic
completo). Este spec no repite su contenido — lo cita por sección. Un spec que parafrasea un
documento que ya existe es [E-039](../errors/E-039-el-contrato-parafrasea-una-definicion-que-ya-existe.md).

## Criterios de aceptación

Los doce siguientes son los de `.agents/features.json` para F-031, transcritos tal cual — son
vinculantes y no se reescriben ni reordenan. El `qa` los verifica **ejecutando cada uno**, no
leyendo código.

1. `npx prisma migrate dev` aplica la migración sobre una base CON datos sin reescribir ninguna
   tabla: todos los campos nuevos de `Venta`, `CierrePeriodo` y `MovimientoStock` son nullable o
   llevan default. Verificado con `\d` sobre las tres tablas en `psql` antes y después.
2. `npx prisma generate`, `npx tsc --noEmit` y `npx vitest run` terminan sin error. El lint se
   corre SOLO, sin pipe: `npm run lint | head` devuelve el exit code de `head` y ha firmado tres
   falsos verdes (E-045).
3. Una venta anterior a la migración queda con `creditoBase = 0` y `clienteId` NULL, y el GET del
   cierre que la contiene devuelve EXACTAMENTE las mismas cifras que antes de migrar. Verificado
   guardando la respuesta del endpoint antes de migrar y comparándola después.
4. `buildResumenMonedas` y `buildResumenPropinas`, ante una línea de pago cuyo tipo no es `cash`
   ni `transfer`, NO la suman a `totalTransfer` NI a `equivalenteBase`, y dejan un aviso.
   Verificado con un test que les pasa una línea `{tipo:'xxx'}` y comprueba que el resumen no se
   mueve en NINGUNO de los dos campos. Hoy esa línea entra por partida doble: como transferencia
   dentro del `else`, y como `equivalenteBase` fuera del `if`.
5. `computeSaldoAlCierre` resta `ABONO`, `AJUSTE_DEVOLUCION` y `CONDONACION` y SUMA
   `REVERSION_ABONO`. Los cuatro tipos se ejercitan en el mismo test: una implementación que reste
   los cuatro pasa el caso de `ABONO` y falla este (E-008).
6. `buildCuentasPorCobrarSnapshot` calcula la antigüedad contra el instante `at` que recibe, no
   contra la hora actual. Verificado SIN mockear el reloj: dos llamadas con el mismo `at`
   separadas en el tiempo devuelven el mismo número de días.
7. `buildCuentasPorCobrarSnapshot` descarta las cuentas con saldo menor o igual a 0.01 y ordena
   por `fechaVenta` ascendente.
8. `bucketAntiguedad` clasifica correctamente los bordes exactos 30, 31, 60, 61, 90 y 91, más el
   caso de 0 días y el de una fecha futura. Verificado con `it.each` sobre los ocho valores — y
   comprobando antes que el símbolo existe, porque un `it.each` con un símbolo inexistente tumba
   el archivo entero en silencio (E-019).
9. La función pura de la invariante acepta `Σ pagos − Σ vuelto + creditoBase = total + tipTotal`
   dentro de `SALE_TOTAL_TOLERANCE_BASE` y rechaza los cuatro casos prohibidos: crédito con
   vuelto, crédito con propina, crédito mayor que el total, y un desajuste por encima de la
   tolerancia. Con `creditoBase = 0` devuelve lo mismo que el comportamiento actual para todos los
   casos que hoy pasan (test de no-regresión).
10. `splitRefundBetweenDebtAndCash` reparte deuda primero: con reembolso 800 y saldo 500 devuelve
    500 a deuda y 300 en efectivo; con saldo 0 devuelve todo en efectivo, que es el comportamiento
    de hoy.
11. `withTenantScope('cuentaPorCobrar', {id}, 'N1')` produce `{id, tienda:{negocioId:'N1'}}` y
    `withTenantScope('movimientoCuentaPorCobrar', {id}, 'N1')` produce el camino anidado por
    cuenta. Verificado con test; sin las entradas en `TENANT_RELATION_PATH` el tipo ni siquiera
    compila, que es la red que se quiere.
12. `pagoLineaSchema` SIGUE rechazando `{tipo:'credit'}`. Es el test que documenta que el crédito
    no es una forma de pago, y lo que impide que alguien revierta la decisión central sin darse
    cuenta.

No se añaden criterios adicionales: los doce ya cubren migración, no-regresión, los tres bugs
latentes que le tocan a este feature (el 4, endurecimiento de caja) y el aislamiento multi-tenant
de las dos entidades relacionales nuevas (el 11) — el `Cliente` en sí no lleva `withTenantScope`
propio en este feature (el dosier fija «dos entradas», no tres); ver «Preguntas abiertas» sobre a
quién le toca la de `Cliente`.

## Contexto necesario

### El documento que gobierna este feature

`.agents/cuentas-por-cobrar.md` es la lectura obligatoria. Seis secciones concretas aplican
directamente a lo que aquí se construye:

- **§2 La decisión central** — el crédito es `Venta.creditoBase`, nunca una línea de
  `pagosDetalle`. `pagoLineaSchema.tipo` se queda en `z.enum(["cash","transfer"])` (criterio 12).
  Las cuatro razones verificadas en código explican por qué no se amplía el enum; la función de
  `creditInvariant.ts` (criterio 9) es la codificación de las «reglas duras» de esa sección — pero
  **su aplicación en servidor (400/409 en las rutas de venta) es de F-034, no de este feature**.
- **§3 Por qué la caja sigue cuadrando sola** — `buildResumenMonedas` arma la gaveta iterando
  `pagosDetalle`/`vueltoDetalle` y nunca mira `Venta.totalcash`. Por eso una venta a crédito no
  aporta nada a caja sin tocar el motor: ese comportamiento **no se toca en F-031**, solo se
  endurece la rama del `else` (criterio 4).
- **§5 Vocabulario** — nombres que fijan los otros ocho features. En particular:
  `CuentaPorCobrar.settledAt IS NULL` = cuenta viva; `MovimientoCuentaPorCobrar` es **append-only**
  (una reversión es una fila nueva, `REVERSION_ABONO`, nunca un `DELETE` ni un `UPDATE`); la deuda
  se denomina siempre en moneda base, y `monedaDeudaCode`/`montoDeudaMonedaOriginal` son solo
  referencia informativa — denominarla en divisa rompería la idempotencia del recálculo de
  `totalPorCobrarAlCierre` de un cierre ya cerrado.
- **§6, columna «Caja»** — la fila de `caja.ts:144` y `tips.ts:127` en la tabla de auditoría es la
  que asigna el endurecimiento a F-031 específicamente (el resto de esa tabla es de otros
  features; no hace falta releerla entera para este feature, solo esa fila).
- **§7 La antigüedad se calcula contra el corte** — `buildCuentasPorCobrarSnapshot` recibe un `at`
  y calcula contra él, nunca contra `Date.now()`. Es exactamente el criterio 6, y la razón es que
  recalcular un cierre viejo debe dar la misma antigüedad cada vez que se ejecuta.
- **§9 Mapa de propiedad** — confirma que ningún otro feature toca los archivos de este spec, y que
  este feature no toca los de ningún otro.

### El precedente a espejar en el schema

`ProductoProveedorLiquidacion` (`prisma/schema.prisma:848-869`) es el mismo problema al revés:
mercancía recibida y aún no pagada al proveedor. Su `liquidatedAt IS NULL` (línea 857) significa
exactamente lo que aquí significará `CuentaPorCobrar.settledAt IS NULL`: devengado y no liquidado.
`Proveedor` (`prisma/schema.prisma:802-829`) es el molde de `Cliente`: mismos campos
(`nombre`, `descripcion`, `direccion`, `telefono`), mismo `@@unique([nombre, negocioId])` (línea
827) y mismo `@@index([nombre])` (línea 828) — pero `Cliente` además necesita **soft delete**, que
`Proveedor` no tiene. El patrón de soft delete ya existe en el schema con la forma
`deletedAt DateTime? // null = activo, fecha = soft delete` (usado, por ejemplo, en
`prisma/schema.prisma:397` y `:447`) — reutilizar esa forma, no inventar una columna `activo`
paralela.

### Dónde tocar `caja.ts` y `tips.ts`, y qué NO cambiar

- `buildResumenMonedas` está en `src/lib/movimiento/caja.ts:144`. El bug concreto: en las líneas
  168-169, `if (pago.tipo === "cash") map[...].totalEfectivo += pago.monto; else
  map[...].totalTransfer += pago.monto;` — y en las líneas 170-175, el `equivalenteBase` se suma
  **fuera de ese `if`**, para cualquier `tipo`. Una línea con un tipo desconocido hoy entra como
  transferencia y como equivalente base a la vez. El arreglo (criterio 4) es sacar el
  `equivalenteBase` de la rama muerta y no sumar nada cuando `pago.tipo` no es ni `"cash"` ni
  `"transfer"`, dejando un aviso.
- `buildResumenPropinas` está en `src/lib/tips.ts:127`, con la misma forma exacta en las líneas
  152-159 (`tipCash`/`tipTransfer` en el `if`/`else` de la 152-153, `equivalenteBase` fuera en la
  154-159).
- `validateTip` (`src/lib/tips.ts:54-111`) **no se toca**. Su primera línea útil,
  `const requested = Number(tipTotal) || 0; if (requested <= 0) return { ok: true, ... };`
  (líneas 63-64), es la razón por la que la regla dura «`creditoBase > 0 ⟹ tipTotal === 0`» hace
  que esta función nunca vea una propina en una venta a crédito. Confirmado leyendo el código: no
  hace falta ningún cambio aquí, y no forma parte de ningún criterio de F-031.
- El endurecimiento **no es solo para el crédito**: cierra la trampa para cualquier tipo de pago
  futuro (vales, puntos). Es la única parte de F-031 que sobrevive intacta si el epic completo se
  descartara.

### `TENANT_RELATION_PATH` — dónde y qué forma

Vive en `src/constants/tenantScope.ts:14-28` (no en `src/lib/tenantScope.ts`, que es donde vive la
función `withTenantScope` que lo consume, en `src/lib/tenantScope.ts:129`). Hoy tiene doce entradas
(`tienda`, `producto`, `usuario`, `proveedor`, `tasaCambio`, `transferDestinations`,
`cierrePeriodo`, `productoTienda`, `venta`, `movimientoStock`, `cashBreakdownCierre`,
`cashBreakdownMoneda`, `productoProveedorLiquidacion`) con la nota `[] significa que el modelo
lleva la columna negocioId directamente`. El criterio 11 exige que:

- `cuentaPorCobrar` produzca `{id, tienda: {negocioId}}` — un solo salto, así que
  `CuentaPorCobrar` necesita una relación directa a `Tienda` (no solo a través de `Venta`).
- `movimientoCuentaPorCobrar` produzca el camino anidado por cuenta (`cuentaPorCobrar: {tienda:
  {negocioId}}`), dos saltos — así que `MovimientoCuentaPorCobrar` se relaciona con
  `CuentaPorCobrar`, no directamente con `Tienda`.

`Cliente` **no** entra en estas dos entradas nuevas: el dosier fija «dos entradas», no tres. Ver
«Preguntas abiertas».

### Schemas Zod existentes que este feature extiende

- `src/schemas/pago.ts:4-9` define `pagoLineaSchema` con `tipo: z.enum(["cash", "transfer"])` —
  **este enum no cambia** (criterio 12). `IPagoLinea` se exporta en la línea 67 vía
  `z.infer<typeof pagoLineaSchema>`; `MovimientoCuentaPorCobrar.pagosDetalle` (dosier §5) reutiliza
  esta misma forma verbatim, no una redefinición.
- `src/schemas/venta.ts` define `ventaSchema` (línea 35 en adelante) con los campos actuales de
  `Venta`; `IVenta` se exporta en la línea 83. Las extensiones de este feature son
  `creditoBase`/`clienteId`, reflejando las columnas nuevas de Prisma.
- `SALE_TOTAL_TOLERANCE_BASE` vive en `src/constants/venta.ts:15` (valor `0.01`) y ya lo usa
  `reconcileSaleTotal` en `src/lib/saleTotal.ts:62-76` para el mismo tipo de comparación con
  tolerancia. La función de la invariante (criterio 9) debe importar esta constante, no
  redefinirla — sería la misma definición parafraseada en dos sitios (E-039).

### Reglas de negocio no evidentes

- **La deuda vive y se calcula toda en moneda base.** `monedaDeudaCode` y
  `montoDeudaMonedaOriginal` son solo para mostrarle al cliente cuánto debe en su divisa; ningún
  cálculo de saldo, antigüedad o invariante opera sobre ellos.
- **El log de movimientos es append-only por diseño, no por descuido.**
  `totalPorCobrarAlCierre` de un período cerrado se recomputa como «movimientos con
  `fecha <= fechaFin`»; si algún día alguien necesita deshacer un abono, es una fila nueva
  (`REVERSION_ABONO`), nunca un `UPDATE` ni un `DELETE` sobre la fila original.
- **`saldoPendiente` es denormalizado.** Se deriva de `montoOriginal` menos la suma de sus
  movimientos, y puede desincronizarse si algo escribe en la tabla sin pasar por el camino
  correcto — pero ese camino (el helper único de escritura) no es parte de este feature; ver
  «Preguntas abiertas».
- **`Venta.creditoBase = 0` es el valor de toda venta anterior a la migración** — no NULL. Es lo
  que hace posible el criterio 1 (migración aditiva) y el 3 (no-regresión de cifras).

### Convención de idioma en el schema

Modelos y columnas de Prisma nuevos van **en español**, igual que el resto de `schema.prisma`
(`PedidoEntrante` y `OutboxEvento` son el precedente reciente); los comentarios `///` van en
inglés; todo símbolo TypeScript nuevo (funciones, tipos, tests) va en inglés, según `AGENTS.md`.

### Errores conocidos a los que este feature es especialmente propenso

- **E-008** — el test del criterio 5 (los cuatro tipos de movimiento de saldo) y el del criterio 3
  (no-regresión de cifras) deben sembrar el dato que hace divergir las dos ramas comparadas: una
  implementación que solo resta `ABONO` pasaría un test que solo prueba `ABONO`.
- **E-015** — `computeSaldoAlCierre`, `buildCuentasPorCobrarSnapshot`, `bucketAntiguedad`,
  `splitRefundBetweenDebtAndCash` y la función de la invariante van en `.ts` planos dentro de
  `src/lib/cuentasPorCobrar/`, nunca en un `.tsx`, aunque el único consumidor inicial fuera un
  componente: un símbolo en un `.tsx` no es importable desde ningún test.
- **E-019** — el `it.each` del criterio 8 sobre `bucketAntiguedad` debe comprobar primero que el
  símbolo existe (o usar un guard `?? []`) mientras `dev-tester` e `implementer` trabajan en
  paralelo sin verse: un símbolo `undefined` en la parametrización tumba el archivo entero, no
  solo ese caso.
- **E-045** — `npm run lint` se corre solo, nunca canalizado (`| head`, `| grep`): el exit code de
  un pipe es el del último comando de la tubería, no el de `lint`.
- **E-052** — no correr `npx prisma format` al tocar `schema.prisma`. Reformatea modelos ajenos que
  no tienen nada que ver con este feature y ensucia un diff que debe ser atómico. Verificar después
  con `git diff --stat prisma/schema.prisma`: inserciones esperadas, cero borrados en modelos que
  no sean los tres nuevos ni las columnas añadidas.
- **E-047** — si la migración o los schemas se editan con un script sobre varios archivos a la vez,
  insertar antes de la línea-ancla, nunca sustituirla: un `replace` sobre la firma de una función
  vecina puede borrar el import que la acompaña, lejos del punto de edición.

## Preguntas abiertas

1. **¿Quién implementa `applyMovimientoCuentaPorCobrar(tx, cuentaId, movimiento)` y
   `scripts/recalculate-cuentas-por-cobrar.ts`?** El dosier §5 los describe como necesarios («debe
   ser la única forma de insertar ahí») pero ninguno de los doce criterios de F-031 los ejercita,
   y el mapa de propiedad del dosier §9 no los asigna explícitamente a ningún feature. Si F-031 no
   los entrega, el primer feature que escriba en `MovimientoCuentaPorCobrar` (¿F-034 al crear la
   venta con `CuentaPorCobrar`? ¿F-035 al registrar un abono?) tendría que crearlos sin contrato
   previo, arriesgando una segunda implementación del mismo helper.
2. **¿`Cliente` necesita su propia entrada en `TENANT_RELATION_PATH`?** El dosier fija «dos
   entradas» (`cuentaPorCobrar`, `movimientoCuentaPorCobrar`) para F-031, y `Cliente` — que sí
   lleva `negocioId` directo, como `Proveedor` — no está entre ellas. Si `api/clientes/**` (F-033)
   necesita `withTenantScope("cliente", ...)`, esa tercera entrada tendría que añadirse ahí, fuera
   de este feature, y quedaría sin ser parte del mismo commit atómico que crea el modelo.

### 2.1 `Cliente`

Molde de `Proveedor` (`prisma/schema.prisma:802-829`) más el soft delete que `Proveedor` no tiene.

```prisma
/// The debtor of a credit sale. Mirrors Proveedor, plus soft delete.
model Cliente {
  id          String   @id @default(uuid())
  nombre      String
  descripcion String?
  direccion   String?
  telefono    String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  negocio   Negocio @relation(fields: [negocioId], references: [id])
  negocioId String

  /// null = active, a date = soft deleted. Same shape as Producto/ProductoTienda.
  deletedAt DateTime?

  ventas           Venta[]
  cuentasPorCobrar CuentaPorCobrar[]

  @@unique([nombre, negocioId])
  @@index([nombre])
}
```

`Negocio` recibe la relación inversa `clientes Cliente[]`.

**Consecuencia asumida y escrita a propósito:** `@@unique([nombre, negocioId])` cuenta también las
filas con `deletedAt` no nulo, así que dar de alta un cliente con el nombre de uno borrado
devolverá `P2002`. Es el mismo comportamiento que ya tiene `Proveedor` sin soft delete. Resolverlo
—reactivar en vez de recrear— es de **F-033**, que es quien escribe `api/clientes/**`; F-031 no
añade ninguna guarda para ello (E-032: una rama que ningún criterio ejercita).

`@@unique([nombre, negocioId])` es además el eje de idempotencia del alta offline de cliente
(dosier § 11, E-043): no se abre una segunda columna `@unique` global para eso.

#### Borrar en blando a un cliente que debe dinero — decisión

Planteado por A1 de `.agents/security/F-031.md`. El modelo `Cliente` es de F-031, así que la regla
se decide aquí aunque la aplique otro feature. **Poner `deletedAt` no toca ninguna
`CuentaPorCobrar`**: es un `UPDATE`, no un `DELETE`, así que ningún `onDelete` se dispara y la deuda
sigue existiendo con su `saldoPendiente` intacto. El patrón estándar de este repo es que los
lectores filtren por `deletedAt: null` (`Producto`, `ProductoTienda`), y con eso un deudor borrado
desaparecería de los listados mientras su deuda sigue en la base. **Una deuda que se vuelve
invisible al borrar al deudor es un agujero contable**, no solo de seguridad: es dinero que el
negocio cree cobrado porque ya no lo ve.

**La regla, en dos mitades:**

1. **La puerta.** `DELETE /api/clientes/[id]` devuelve **409** si el cliente tiene alguna
   `CuentaPorCobrar` con `settledAt IS NULL`. Primero se salda o se condona la deuda, después se
   borra al cliente. **Lo comprueba F-033**, que es dueño de `api/clientes/**` (dosier § 9), en esa
   ruta, y lo verifica ejecutando el DELETE contra un cliente con una cuenta viva. Es el mismo molde
   que el 409 de F-037 para «no se puede borrar una venta con abonos».
2. **La red de detrás.** Ninguna vista que muestre un saldo pendiente —el panel de F-035, los
   reportes de F-039, las cifras de cierre de F-032— filtra las cuentas por `Cliente.deletedAt`. Si
   una cuenta viva aparece bajo un cliente borrado, se muestra **anotada** («cliente eliminado»),
   nunca oculta.

La segunda mitad no es redundante con la primera. La puerta cierra el camino de la API; una fila
puede llegar a ese estado por otras vías —una escritura directa a la base, o una venta a crédito que
se sincroniza tarde contra un cliente borrado entretanto—, y en ese caso la elección es entre verla
o no verla. Se ve.

**Se descartó la opción de permitir el borrado y confiar solo en la mitad 2**, que era la
alternativa que el informe planteaba: obliga a que **todos** los lectores futuros recuerden no
filtrar, que es un requisito negativo repartido entre cuatro features y decae en cuanto uno lo
olvide. Una guarda en un sitio se verifica ejecutándola; una disciplina en cinco, no.

**Nada de esto lo implementa F-031**, y no hay que confundirlo: ningún criterio de aceptación de
F-031 lo ejercita, no hay ruta que escribir aquí y `Cliente` no cambia de forma por esta decisión.
Lo que F-031 aporta es la regla escrita, para que F-033 no la invente al llegar al DELETE.

### 2.2 `CuentaPorCobrar`

```prisma
/// The debt of one credit sale. `settledAt IS NULL` = live, exactly as
/// ProductoProveedorLiquidacion.liquidatedAt means "accrued and not settled".
model CuentaPorCobrar {
  id String @id @default(uuid())

  /// The credit sale that created the debt. UNIQUE: one account per sale.
  venta   Venta  @relation(fields: [ventaId], references: [id], onDelete: Cascade)
  ventaId String @unique

  cliente   Cliente @relation(fields: [clienteId], references: [id])
  clienteId String

  /// Direct edge to Tienda. It exists so the tenant clause is ONE hop
  /// (TENANT_RELATION_PATH.cuentaPorCobrar = ["tienda"]), not two through Venta.
  ///
  /// INVARIANT: this MUST equal the tiendaId of the Venta that created the row. Nothing in
  /// the schema enforces it — there is no composite FK against a simple FK — so the writer
  /// (F-034, which creates this row inside the same $transaction as the Venta) derives it
  /// from the SAME variable already persisted as Venta.tiendaId. It is never re-read from
  /// the request, from a route param, or from another part of the payload.
  tienda   Tienda @relation(fields: [tiendaId], references: [id])
  tiendaId String

  /// Copied from Venta.createdAt when the account is created. Aging is measured from here.
  fechaVenta DateTime

  /// Venta.creditoBase at creation, in base currency.
  montoOriginal Float @default(0)

  /// DENORMALIZED: montoOriginal minus the signed sum of its movements.
  /// computeSaldoAlCierre is the definition; this column is a cache of it.
  saldoPendiente Float @default(0)

  /// NULL = live account. A date = fully settled.
  settledAt DateTime?

  /// Informative only, so the customer can be told "you owe 20 USD". No arithmetic
  /// reads these: the debt is denominated in base currency (ADR 0111).
  monedaDeudaCode          String?
  montoDeudaMonedaOriginal Float?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  movimientos MovimientoCuentaPorCobrar[]

  @@index([tiendaId, settledAt])
  @@index([tiendaId, fechaVenta])
  @@index([clienteId])
}
```

**El invariante de `tiendaId`, y por qué está escrito en el comentario de la columna** (B1 de
`.agents/security/F-031.md`). `TENANT_RELATION_PATH.cuentaPorCobrar` confía en
`CuentaPorCobrar.tienda` como **el único salto** hacia `negocioId`. Si una fila naciera con un
`tiendaId` distinto al de su propia venta, pasaría `withTenantScope("cuentaPorCobrar", …)` bajo el
negocio equivocado: el camino sería correcto y la fila estaría colgada del tenant que no es. Nada en
el schema lo impide —una FK simple a `Tienda` no puede exigir que coincida con la de `Venta`—, así
que la garantía la sostiene **la disciplina del escritor**, y por eso va escrita en el comentario de
la columna y no solo aquí: F-034 va a leer el comentario, no esta auditoría.

Es la misma disciplina de «una sola variable, leída una vez» que este repo ya exige para el
`negocioId` de los emisores del outbox. F-031 **no la comprueba**: no hay escritor todavía. Quien la
tiene que sostener y verificar ejecutando es **F-034**, que es dueño de las dos rutas de venta.

Los tres índices cubren los tres accesos que el epic ya tiene escritos: las cuentas vivas de una
tienda (panel de F-035), el filtro del corte de F-032 —`tiendaId` + `fechaVenta <= corte`, dosier
§ 7— y las cuentas de un cliente (F-033). **No se ha medido ningún plan**: la tabla nace vacía y
medir un plan sobre una tabla sin filas no dice nada (E-023). Quien tenga filas reales —F-032 o
F-035— es quien puede contrastarlos.

Estos índices se crean junto con la tabla, que está vacía: no aplica el problema del ADR 0002
(`CREATE INDEX CONCURRENTLY`), que existe para índices sobre tablas calientes y ya pobladas.

### 2.3 `MovimientoCuentaPorCobrar`

```prisma
/// APPEND-ONLY ledger of everything that moves a balance. A reversal is a new row
/// (REVERSION_ABONO), never an UPDATE or a DELETE: totalPorCobrarAlCierre of a closed
/// period is recomputed as "movements with fecha <= fechaFin", and mutating rows would
/// change the figures of an already closed period.
model MovimientoCuentaPorCobrar {
  id String @id @default(uuid())

  /// Relation field named `cuentaPorCobrar` on purpose: TENANT_RELATION_PATH walks
  /// relation FIELD names, and criterion 11 fixes the clause as
  /// { cuentaPorCobrar: { tienda: { negocioId } } }.
  cuentaPorCobrar   CuentaPorCobrar @relation(fields: [cuentaPorCobrarId], references: [id], onDelete: Cascade)
  cuentaPorCobrarId String

  tipo TipoMovimientoCuentaPorCobrar

  /// Always POSITIVE and always in base currency. The sign belongs to `tipo`, never
  /// to this number: see MOVIMIENTO_CUENTA_POR_COBRAR_SIGN in src/lib/cuentasPorCobrar/saldo.ts.
  monto Float

  /// When the movement happened. This is what assigns it to a period: there is
  /// deliberately NO cierrePeriodoId FK (see the note below).
  fecha DateTime @default(now())

  /// IPagoLinea[] — the SAME shape as Venta.pagosDetalle, so buildResumenMonedas
  /// consumes sales and collections through one function. NULL for the tipos that
  /// move no physical money (CONDONACION, AJUSTE_DEVOLUCION).
  pagosDetalle Json?
  /// Rates in force when this movement was registered. Its own snapshot: an
  /// instalment happens weeks after the sale, with different rates.
  tasaSnapshot Json?

  motivo String?

  usuario   Usuario? @relation(fields: [usuarioId], references: [id])
  usuarioId String?

  /// A REVERSION_ABONO points at the ABONO it reverses. NULL for every other tipo.
  /// F-031 creates this column and writes nothing into it; F-035 is its first writer.
  ///
  /// SELF-REFERENCING FK, and the database only checks that the target row EXISTS: it does
  /// not check that it belongs to the same cuentaPorCobrarId, and therefore not that it
  /// belongs to the same tenant. The check lives in applyMovimientoCuentaPorCobrar (§ 9),
  /// which is the only door that writes here.
  revierte    MovimientoCuentaPorCobrar?  @relation("ReversionAbono", fields: [revierteId], references: [id])
  revierteId  String?
  reversiones MovimientoCuentaPorCobrar[] @relation("ReversionAbono")

  createdAt DateTime @default(now())

  @@index([cuentaPorCobrarId, fecha])
  @@index([fecha])
}
```

`Usuario` recibe la relación inversa `movimientosCuentaPorCobrar MovimientoCuentaPorCobrar[]`.

**Por qué no hay `cierrePeriodoId`.** Un abono pertenece al período que estaba abierto cuando
ocurrió, y eso ya lo dice `fecha`. Una FK al cierre sería una **segunda representación del mismo
hecho** —la misma razón por la que el crédito no es una línea de `pagosDetalle` (ADR 0111, razón 4)—
y podría desincronizarse de `fecha` cuando un cierre se recalcula. F-032 asigna el movimiento a su
período por rango de fechas, igual que hace hoy con `MovimientoStock` en `loadCierreInput.ts`.

**Idempotencia de un abono.** Cuando F-035 la necesite, usa la tabla genérica `IdempotencyKey`
(`prisma/schema.prisma:726`), que ya lleva el `negocioId` como eje en su columna `scopeId`. No se
añade aquí una columna `@unique` global (E-043), ni se intenta recuperar un `P2002` dentro de la
misma transacción (E-038).

**Advertencia para F-035, que es quien la va a consumir** (M3 de `.agents/security/F-031.md`).
`IdempotencyKey.key` es **`@id` global**, no una clave compuesta con `scopeId`: el comentario del
modelo afirma que «una clave solo se busca dentro de su propio scope», pero eso es una promesa del
que consulta, no algo que la tabla imponga. Es el mismo patrón que E-043 documentó para
`Venta.syncId`: una columna de idempotencia única a nivel global es un eje de tenant más, y un
`findUnique({ where: { key } })` a secas dejaría que un negocio leyera la respuesta cacheada de otro
adivinando o reutilizando su `key`.

La forma de no tropezar con esto es **no consultar la tabla directamente**: `src/lib/idempotency.ts`
ya expone `claimIdempotencyKey` y `findIdempotentResponse`, y el segundo hace
`findFirst({ where: { key, scopeId, endpoint } })` (`src/lib/idempotency.ts:106-107`). Quien reclame
o lea una clave usa esos dos helpers. F-031 no toca esta tabla ni la consulta.

### 2.4 El enum: **enum de Prisma**, no `String`

```prisma
/// Everything that can move a CuentaPorCobrar balance. Values in Spanish, like
/// MovimientoTipo and FormaPagoCompra: they are persisted, listed and labelled
/// next to those. Every TypeScript symbol around them is in English.
enum TipoMovimientoCuentaPorCobrar {
  ABONO             // Money received against the debt. Lowers the balance.
  AJUSTE_DEVOLUCION // Refund of returned goods applied to the debt. Lowers the balance.
  CONDONACION       // Debt written off. Lowers the balance.
  REVERSION_ABONO   // Undoes an earlier ABONO. RAISES the balance.
}
```

**Justificación (decisión 2).** El repo hace las dos cosas y la línea que las separa es de quién es
el dominio del valor:

- `MovimientoTipo`, `FormaPagoCompra` y `MovimientoState` son **enums de Prisma**, con su espejo
  Zod en `src/schemas/movimiento.ts` y sus listas en `src/constants/movimientos.ts`. Su dominio es
  nuestro y está cerrado.
- `PedidoEntrante.status`, `cancelledBy` y `currencyCode` son **texto libre** por el ADR 0004: su
  dominio lo posee queandabuscando y puede crecer sin avisarnos.

Aquí el dominio es nuestro y está cerrado por el dosier § 5 en cuatro valores. Y hay un segundo
motivo, que es el que decide: **el signo de cada tipo es una regla de negocio** que
`computeSaldoAlCierre` codifica (criterio 5), y un enum permite declararla como
`Record<ITipoMovimientoCuentaPorCobrar, 1 | -1>`, que `tsc` obliga a completar. Es la misma red que
el ADR 0071 describe para los cuatro `Record<ITipoMovimiento, …>` de `src/constants/movimientos.ts`.

La adenda de E-035 —«un campo cuyo dominio solo se conoce al recorrer los datos nace como texto
libre»— no aplica: aquí no hay censo que recorrer, los cuatro valores están decididos.

Coste asumido: añadir un quinto valor en el futuro exige una migración (`ALTER TYPE … ADD VALUE`) y
completar el mapa de signos. Es exactamente el coste que hace visible el cambio.

### 2.5 Columnas aditivas en tablas con datos

Todas nullable o con `@default` — es lo que sostiene el **criterio 1**.

`Venta`:

```prisma
  /// Portion of `total` handed over on credit, in base currency. 0 = fully paid at
  /// the counter, which is every sale created before this column existed.
  creditoBase Float @default(0)

  /// The debtor. NULL <=> creditoBase = 0.
  cliente   Cliente? @relation(fields: [clienteId], references: [id])
  clienteId String?

  cuentaPorCobrar CuentaPorCobrar?
```

`CierrePeriodo`:

```prisma
  /// Sum of Venta.creditoBase of the period. INSIDE totalVentas, OUTSIDE the drawer.
  totalCreditoOtorgado   Float @default(0)
  /// Debt collected during this period, whatever period the debt was born in.
  /// INSIDE the drawer, OUTSIDE totalVentas.
  totalCobrosCredito     Float @default(0)
  /// Store balance still outstanding at fechaFin, across all periods. A STOCK, not a
  /// flow: never summed across periods.
  totalPorCobrarAlCierre Float @default(0)
```

`MovimientoStock`:

```prisma
  /// Only for DEVOLUCION_VENTA on a credit sale: how much of montoReembolso was applied
  /// to the debt instead of leaving the drawer. Cash actually returned is
  /// montoReembolso - (montoAplicadoADeuda ?? 0). NULL for every movement recorded
  /// before this column existed and for every refund of a non-credit sale.
  montoAplicadoADeuda Float?
```

**Por qué el criterio 1 se cumple, con su cualificación.** `ALTER TABLE … ADD COLUMN … NULL` no
reescribe la tabla en ninguna versión soportada; `ADD COLUMN … NOT NULL DEFAULT <constante>` tampoco
la reescribe **en PostgreSQL 11 y posteriores**, donde el default se guarda como metadato. Esa es la
cualificación que el criterio hay que verificar ejecutando —`\d` antes y después— y no dar por buena
leyendo esto. La FK nueva de `Venta.clienteId` sí obliga a Postgres a validar la restricción, que es
un escaneo, no una reescritura: `\d` mostrará la misma definición de columnas más la nueva.

**Ninguna columna nueva cambia el valor de ninguna cifra existente**, que es lo que sostiene el
criterio 3: `creditoBase` nace en 0 y todo lector actual de `Venta` ignora la columna.

### 2.6 F-031 no añade ningún índice a `Venta` (decisión 6)

`@@index([clienteId])` sobre `Venta` sería útil para «las ventas de un cliente», pero **ningún
criterio de F-031 lo ejercita** y `Venta` es una de las tablas calientes del sistema: un
`CREATE INDEX` normal toma un lock que bloquea las escrituras mientras construye, y la vía
`CONCURRENTLY` exige su propia migración escrita a mano (ADR 0002). Ese coste le toca al feature que
tenga de verdad la consulta —F-033 o F-037—, con filas reales para medirlo (E-023).

## 3. Schemas Zod

### 3.1 El grafo de imports, y por qué no tiene ciclos (E-028)

Aristas que este feature añade, todas en un solo sentido:

```
schemas/cuentaPorCobrar.ts  ->  schemas/pago.ts
schemas/cuentaPorCobrar.ts  ->  schemas/tasaCambio.ts
schemas/cliente.ts          ->  (nada)
```

**Regla dura, y es la que evita el ciclo:** `src/schemas/pago.ts` y `src/schemas/venta.ts` **no
importan nada** de `cuentaPorCobrar.ts` ni de `cliente.ts`. Por eso `ventaSchema` recibe `clienteId`
como `z.string().uuid()` y no un `clienteSchema` anidado: un campo escalar no crea arista. Un ciclo
de valor entre dos módulos de schemas da `tsc` en verde y revienta al cargar, tumbando archivos de
test ajenos al feature.

### 5.2 `src/lib/cuentasPorCobrar/aging.ts`

```ts
import { computeSaldoAlCierre } from "@/lib/cuentasPorCobrar/saldo";
import type { ICuentaPorCobrarMovimientoSaldo } from "@/lib/cuentasPorCobrar/saldo";

/**
 * The aging brackets, in order, with the UPPER bound of each one in days. THE ONLY
 * definition of the brackets in the project (E-014): `bucketAntiguedad` is its only
 * interpreter, and every screen, report and closing figure that shows aging reads the
 * bucket this function returns instead of restating the numbers.
 *
 * `null` on the last one means "no upper bound".
 */
export const AGING_BUCKETS = [
  { bucket: "0-30", maxDays: 30 },
  { bucket: "31-60", maxDays: 60 },
  { bucket: "61-90", maxDays: 90 },
  { bucket: "91+", maxDays: null },
] as const;

export type IAgingBucket = (typeof AGING_BUCKETS)[number]["bucket"];

/** Milliseconds in a day. */
const MS_PER_DAY = 86_400_000;

/**
 * Whole days elapsed between `fechaVenta` and `at`, floored. Negative when `fechaVenta`
 * is later than `at` (a sale dated in the future), and that negative value is returned,
 * not clamped: `bucketAntiguedad` is what decides where it lands.
 */
export function daysOutstanding(fechaVenta: Date, at: Date): number;

/**
 * Classifies a number of DAYS into its bracket. Takes days, not dates, so the boundary
 * cases of criterion 8 are exactly eight numbers.
 *
 * The first bracket whose `maxDays` is not exceeded wins:
 *
 *   dias <= 30  -> "0-30"    (this is where 0 lands, and any negative one: a sale dated
 *                             in the future has not aged at all)
 *   dias <= 60  -> "31-60"
 *   dias <= 90  -> "61-90"
 *   otherwise   -> "91+"
 *
 * So the six exact boundaries of criterion 8 land: 30 -> "0-30", 31 -> "31-60",
 * 60 -> "31-60", 61 -> "61-90", 90 -> "61-90", 91 -> "91+".
 */
export function bucketAntiguedad(dias: number): IAgingBucket;

/**
 * A balance at or below this, in base currency, is not an open account: it is the cent
 * left over by rounding.
 *
 * Numerically equal to SALE_TOTAL_TOLERANCE_BASE and deliberately NOT the same constant:
 * that one is the gap tolerated between a client's total and the server's, and the two
 * can be tuned for different reasons.
 */
export const MIN_OPEN_BALANCE_BASE = 0.01;

export interface ICuentaPorCobrarSnapshotInput {
  id: string;
  clienteId: string;
  clienteNombre?: string | null;
  fechaVenta: Date;
  montoOriginal: number;
  /** Already filtered by the caller's cutoff, same as computeSaldoAlCierre expects. */
  movimientos: ICuentaPorCobrarMovimientoSaldo[];
}

export interface ICuentaPorCobrarSnapshotRow {
  id: string;
  clienteId: string;
  clienteNombre: string | null;
  fechaVenta: Date;
  montoOriginal: number;
  /** computeSaldoAlCierre over `movimientos`. Greater than MIN_OPEN_BALANCE_BASE. */
  saldo: number;
  /** daysOutstanding(fechaVenta, at). */
  dias: number;
  bucket: IAgingBucket;
}

export interface ICuentasPorCobrarSnapshot {
  /** The instant the whole snapshot was measured against — the `at` it received. */
  at: Date;

  /** Sum of `saldo` per bracket. All four keys are present; an empty bracket is 0. */

  /** Sorted by `fechaVenta` ascending. */
  cuentas: ICuentaPorCobrarSnapshotRow[];
}

/**
 * Aging snapshot of a set of accounts, measured against `at`.
 *
 * `at` is the ONLY clock this function reads: it never calls Date.now(). That is what
 * makes recomputing an old closing give the same aging every time it runs (dosier § 7),

 * moments, return the same `dias`.
```

Comportamiento fijado:

- `at` se devuelve tal cual, sin clonar.

### 5.4 `src/lib/cuentasPorCobrar/creditInvariant.ts`

```ts
import { convertToBase } from "@/lib/currency";
import { SALE_TOTAL_TOLERANCE_BASE } from "@/constants/venta";
import type { IPagoLinea, IVueltoLinea } from "@/schemas/pago";
import type { ITasaSnapshot } from "@/schemas/tasaCambio";

/**
 * The five ways a sale can break the credit invariant, in the order they are evaluated.
 * THE ORDER IS THE CONTRACT and the first one to fire wins — same shape as
 * TENANT_SCOPE_DECISIONS in src/lib/tenantScope.ts.
 *
 * The three hard rules are checked BEFORE the arithmetic on purpose: a sale that breaks
 * one of them usually breaks the sum as well, and the caller needs the reason it can act
 * on, not "the numbers do not add up".
 */
export const CREDIT_INVARIANT_VIOLATIONS = [
  "CREDIT_WITHOUT_CUSTOMER",
  "CREDIT_WITH_CHANGE",
  "CREDIT_WITH_TIP",
  "CREDIT_EXCEEDS_TOTAL",
  "TOTAL_MISMATCH",
] as const;

export type ICreditInvariantViolation =
  (typeof CREDIT_INVARIANT_VIOLATIONS)[number];

/**
 * The HTTP status each violation gets when a sale route rejects with it. Declared here
 * so F-034 does not restate the mapping in two routes.
 *
 * CREDIT_WITHOUT_CUSTOMER is a 409 and not a 400 because `isPermanentSyncError` parks a
 * 409 instead of retrying it forever: an offline sale naming a customer that does not
 * exist has to stop, not spin.
 */
export const CREDIT_INVARIANT_HTTP_STATUS: Record<
  ICreditInvariantViolation,
  400 | 409
> = {
  CREDIT_WITHOUT_CUSTOMER: 409,
  CREDIT_WITH_CHANGE: 400,
  CREDIT_WITH_TIP: 400,
  CREDIT_EXCEEDS_TOTAL: 400,
  TOTAL_MISMATCH: 400,
};

export interface ICreditInvariantInput {
  /** The sale total the server will persist, in base currency, net of discounts. */
  total: number;
  tipTotal?: number | null;
  creditoBase?: number | null;
  clienteId?: string | null;
  pagosDetalle?: IPagoLinea[] | null;
  vueltoDetalle?: IVueltoLinea[] | null;
  tasaSnapshot?: ITasaSnapshot | null;
  monedaBase: string;
  /** Defaults to SALE_TOTAL_TOLERANCE_BASE. */
  tolerance?: number;
}

/**
 * A FLAT shape rather than a discriminated union, for the same reason
 * TipValidationResult in src/lib/tips.ts is flat: `strict` is off in this project, so a
 * boolean discriminant does not narrow (E-036). Callers read `result.violation === null`
 * or `result.ok === true`; `if (!result.ok)` does not narrow anything here.
 */
export interface ICreditInvariantResult {
  ok: boolean;
  /** null when ok. */
  violation: ICreditInvariantViolation | null;
  /** (paid - change + creditoBase) - (total + tipTotal), rounded to two decimals. */
  delta: number;
  /** The credit actually read, after coercion. */
  creditoBase: number;
}

/**
 * Checks the invariant of a sale that may carry credit:
 *
 *   Σ pagosDetalle.equivalenteBase − Σ vueltoDetalle(base) + creditoBase = total + tipTotal
 *
 * The two sums are computed the same way validateTip already computes them
 * (src/lib/tips.ts:88-99): the payments are read from their stored `equivalenteBase`
 * and are NOT reconverted, and the change lines, which carry no equivalenteBase, are
 * converted with `convertToBase` against `tasaSnapshot`. Same definition, one place.
 *
 * F-031 only ships this function. Calling it from the two sale routes and turning a
 * violation into a 400 or a 409 is F-034.
 */
export function checkCreditInvariant(
  input: ICreditInvariantInput,
): ICreditInvariantResult;
```

**El orden de evaluación, escrito para que cada caso del criterio 9 sea discriminable:**

| Orden | Condición | `violation` |
|---|---|---|
| 1 | `creditoBase > 0` y `clienteId` ausente, `null` o cadena vacía | `CREDIT_WITHOUT_CUSTOMER` |
| 2 | `creditoBase > 0` y `Σ vueltoDetalle.monto > 0` | `CREDIT_WITH_CHANGE` |
| 3 | `creditoBase > 0` y `tipTotal > 0` | `CREDIT_WITH_TIP` |
| 4 | `creditoBase > total + tolerance` | `CREDIT_EXCEEDS_TOTAL` |
| 5 | `Math.abs(delta) > tolerance` | `TOTAL_MISMATCH` |
| — | ninguna | `null`, `ok: true` |

Notas que el implementador y el tester necesitan **igual**:

- La condición 2 mira `Σ vueltoDetalle.monto`, la suma cruda de las líneas de vuelto —cualquier
  moneda—, no su equivalente en base. Un vuelto es vuelto en la moneda en que se dio.
- `creditoBase`, `tipTotal`, `total` y los importes se leen con `Number(x) || 0`, así que
  `undefined`, `null` y `NaN` valen 0. **Esa coerción no normaliza negativos**: `Number(-50) || 0`
  da `-50`, porque `-50` es *truthy*. Un `creditoBase` negativo no dispara ninguna de las cinco
  violaciones por sí solo —la 1 y la 3 exigen `creditoBase > 0`, la 4 exige
  `creditoBase > total + tolerance`—, así que **todo llamador tiene que garantizar que su entrada ya
  pasó por `multimonedaExtrasSchema` o `ventaSchema`**, que es donde `.nonnegative()` lo rechaza
  (§ 3.4, § 3.5). Hoy ese es siempre el caso; el camino a vigilar es el que no pase por Zod, como el
  `scripts/recalculate-cuentas-por-cobrar.ts` que el § 9 reserva. La función **no** clampa el
  negativo a propósito: enmascararlo escondería un dato corrupto en vez de dejarlo salir como
  `TOTAL_MISMATCH`, que es la señal útil.
- `CREDIT_WITHOUT_CUSTOMER` es la mitad **pura** de la primera regla dura del dosier § 2. La otra
  mitad —«y del negocio»— es una consulta a la base y la hace **F-034**, no esta función. Ningún
  criterio de F-031 la ejercita: está aquí para que F-034 no invente el código del 409.
- `delta` se devuelve siempre, también cuando `ok` es `true`, para poder registrar la desviación.

**Convivencia con `reconcileSaleTotal` (decisión 5).** `reconcileSaleTotal`
(`src/lib/saleTotal.ts:62`) contesta otra pregunta: **con qué total se persiste la venta**, cliente
contra recomputación del servidor. `checkCreditInvariant` contesta si los movimientos de dinero de
la venta cuadran. No se reutiliza la función; **sí se reutiliza la constante**:
`SALE_TOTAL_TOLERANCE_BASE` se importa de `@/constants/venta` y no se redefine (E-039).

Y un orden que F-034 tiene que respetar, y que se fija aquí porque afecta al diseño:
`reconcileSaleTotal` corre **primero** y `checkCreditInvariant` recibe en `total` la cifra ya
reconciliada, nunca la que reportó el cliente. Validar contra el total del cliente anularía la
única defensa contra una deuda inventada.

**Qué significa exactamente el test de no-regresión del criterio 9,** y esta es la parte que el
diseño tiene que sostener, no el implementador:

- Con `creditoBase = 0` las cuatro primeras violaciones son **inalcanzables**: las tres primeras
  están guardadas por `creditoBase > 0`, y la cuarta por `0 > total + tolerance`, falsa para
  cualquier `total >= 0`. Así que el único desenlace posible es `ok: true` o `TOTAL_MISMATCH`.
- Y `TOTAL_MISMATCH` no se dispara para una venta cuyas líneas ya cumplen
  `Σ pagos − Σ vuelto = total + tipTotal`, que es lo que produce `calcularVuelto`
  (`src/lib/currency.ts:230`) y lo que `validateTip` ya presupone al calcular su `overpayment`.
  Esa es la forma ejecutable de «lo mismo que el comportamiento actual».

**Cualificación honesta, y hay que dejarla escrita (E-017):** este chequeo es **más estricto** que
lo que el servidor hace hoy, porque hoy **nadie comprueba esta igualdad** (dosier § 2, tabla de
reglas duras). Una venta con un sobrepago que no quedó registrado como vuelto
—`Σ pagos − Σ vuelto > total + tipTotal`— hoy se persiste y aquí daría `TOTAL_MISMATCH`. En F-031
eso no cambia nada, porque **ninguna ruta llama a esta función todavía**. Es F-034 quien decide qué
hace con ese caso al cablearla, y quien tiene que verificarlo contra ventas reales antes de
rechazar nada.

## 7. El endurecimiento de los dos agregadores (criterio 4)

### 7.1 `buildResumenMonedas` — `src/lib/movimiento/caja.ts:144`

Hoy, en las líneas 168-175, el bucle de pagos hace esto:

La forma exacta que lo sustituye — **la guarda va antes de crear el bucket de la moneda**:

```ts

        console.warn(UNKNOWN_PAYMENT_LINE_TYPE_WARNING);

      if (!map[pago.moneda])

        pago.monto, pago.moneda, tasas, monedaBase,
```

Tres cosas que quedan fijadas, y las tres importan para el test:

- **La condición que sustituye al `else`** es el `continue` de la guarda: el `else` de la línea 169
  ya solo puede ser `"transfer"`, porque los otros dos casos salieron antes.
- **El `equivalenteBase` se queda donde está**, después del `if`/`else`. Lo que cambia es que una
  línea desconocida ya no llega hasta ahí. Sacarlo de la rama muerta es exactamente esto: la mitad
  que se olvida (dosier § 4).
- **La línea desconocida no crea el bucket de su moneda.** Si es la única línea de esa moneda, esa
  moneda **no aparece** en el array devuelto. Es la lectura fuerte del criterio 4 —«el resumen no se
  mueve»—: ni los dos campos ni el número de filas.

El `import` del aviso: `import { UNKNOWN_PAYMENT_LINE_TYPE_WARNING } from "@/constants/pago";`

Comprobado que `pago.tipo !== "cash" && pago.tipo !== "transfer"` compila con la configuración de
este repo, ejecutando `npx tsc --noEmit` sobre el patrón: el segundo operando compara `"transfer"`
con `"transfer"`, que se solapan, así que no salta TS2367. En tiempo de ejecución la rama sí es
alcanzable, porque `pagosDetalle` viene de una columna `Json` y el `as IPagoLinea[]` de la línea 152
no valida nada.

- Un `console.warn` **por línea infractora**, con la constante como **único argumento** y sin

  `expect(spy).toHaveBeenCalledWith(UNKNOWN_PAYMENT_LINE_TYPE_WARNING)`.
- El volumen del log está acotado por el número de líneas infractoras, que en operación normal es
  cero: hoy `pagoLineaSchema` solo admite dos valores y nada escribe un tercero.
- Las dos funciones emiten **la misma** constante. Un test que necesite distinguir cuál se disparó
  las llama por separado.

```ts
import type { Prisma } from "@prisma/client";
import type { ITipoMovimientoCuentaPorCobrar } from "@/schemas/cuentaPorCobrar";
import type { IPagoLinea } from "@/schemas/pago";
import type { ITasaSnapshot } from "@/schemas/tasaCambio";

export interface INuevoMovimientoCuentaPorCobrar {
  tipo: ITipoMovimientoCuentaPorCobrar;
  /** Positive, in base currency. */
  monto: number;
  /** Defaults to now. */
  fecha?: Date;
  pagosDetalle?: IPagoLinea[] | null;
  tasaSnapshot?: ITasaSnapshot | null;
  motivo?: string | null;
  usuarioId?: string | null;
  /** Only for REVERSION_ABONO: the ABONO being undone. */
  revierteId?: string | null;
}

export interface IMovimientoCuentaPorCobrarApplied {
  movimientoId: string;
  /** The recomputed CuentaPorCobrar.saldoPendiente after the insert. */
  saldoPendiente: number;
  /** Set when the balance reached zero, null while the account is still live. */
  settledAt: Date | null;
}

/**
 * The ONLY way to insert into MovimientoCuentaPorCobrar. Appends the row and recomputes
 * the denormalized CuentaPorCobrar.saldoPendiente and settledAt inside the caller's
 * transaction, so the ledger and its cache cannot diverge.
 *
 * `cuentaId` is the CuentaPorCobrar.id (the column is cuentaPorCobrarId).
 *
 * When `movimiento.revierteId` is present, the implementation verifies, BEFORE inserting,
 * that the referenced row's cuentaPorCobrarId equals `cuentaId` — the same account, and
 * therefore the same tenant. The self-referencing FK only guarantees that the target row
 * exists. A REVERSION_ABONO pointing at another account's ABONO would move a balance that
 * is not its own, and across negocios if the two accounts belong to different ones.
 *
 * This guard is half of why this helper is the only write door: the other half is keeping
 * saldoPendiente in step with the ledger.
 */
export function applyMovimientoCuentaPorCobrar(
  tx: Prisma.TransactionClient,
  cuentaId: string,
  movimiento: INuevoMovimientoCuentaPorCobrar,
): Promise<IMovimientoCuentaPorCobrarApplied>;
```
