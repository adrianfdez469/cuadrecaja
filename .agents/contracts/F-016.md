# F-016: contrato de interfaces

> Escrito por el agente `arch-guardian`. El agente `spec` nunca escribe aquí; el arquitecto nunca
> reescribe `.agents/specs/F-016.md` (la sección «Contrato de interfaces» que ese archivo trae al
> final es residuo de una plantilla vieja: **el contrato es este fichero**).
> `implementer` y `dev-tester` programan contra este fichero **sin verse entre ellos**: es lo único
> que evita que choquen.

**Este documento refleja el estado final acordado, no su historial.**

## 0. Lo que hay que saber antes de leer las firmas

1. **«Omitir no es apagar».** Las cinco claves nuevas del `payload` de `STORE` son opcionales y
   **ausentes dejan la columna intacta** — al revés que los nueve campos de contacto, donde omitir
   borra. Solo viajan las que **cambiaron en esta operación**. De dónde sale ese «qué cambió» es la
   decisión central del feature: [ADR ADRIAN-0152](../../docs/adr/ADRIAN-0152-el-delta-de-la-configuracion-de-compra-sale-de-la-fila.md).
2. **Las columnas de Prisma se llaman como las claves del cable**, en inglés:
   [ADR ADRIAN-0151](../../docs/adr/ADRIAN-0151-las-cinco-columnas-de-compra-se-llaman-como-el-cable.md).
3. **El enum tiene DOS valores, a propósito.** `ZONE_BASED` y `Tienda.zoneCode` son alcance de
   **F-042**. No se añaden aquí, ni «por dejarlo preparado». La forma elegida (constante + `z.enum`
   + columna `String`) admite el tercero sin migración ni reapertura de este contrato: ver
   § 9 «Extensibilidad».
4. **Con `strict: false`, el tipo inferido no es el contrato; el schema en tiempo de ejecución sí.**
   Comprobado con una sonda contra el `tsc` de este repositorio: una clave `.nullable()` dentro de un
   objeto se infiere **opcional y sin el `| null`** (E-079). Nadie debe escribir un test sobre esa
   forma del tipo: se verifica **parseando** (que `null` se acepta o se rechaza), nunca tipando.
5. **Nada de `@testing-library/react`.** Toda la lógica verificable por la suite tiene que vivir en
   un `.ts`; un símbolo dentro de un `.tsx` no es importable desde un test (E-015). La § 10 lista lo
   que el `dev-tester` puede ejercitar.

## 3. Schemas y tipos compartidos — `src/schemas/qabStorePurchaseConfig.ts` (nuevo)

Módulo **client-safe**: lo importan la pantalla, el `PATCH` y el constructor del `payload`. No
importa Prisma ni nada de `src/lib/`.

```ts
/** The wire vocabularies, and the ONE place the two enums are declared as Zod. */
export const qabCheckoutModeSchema = z.enum(QAB_CHECKOUT_MODES);
export type IQabCheckoutMode = z.infer<typeof qabCheckoutModeSchema>;

export const qabDeliveryFeeModeSchema = z.enum(QAB_DELIVERY_FEE_MODES);
export type IQabDeliveryFeeMode = z.infer<typeof qabDeliveryFeeModeSchema>;

/* -- The rules, written ONCE and reused by every border. ------------------ */

/** PURE. Finite, >= 0, at most QAB_AMOUNT_DECIMALS decimals, below the column cap. */
export function isQabDeliveryFee(value: unknown): boolean;

/** PURE. Integer within [QAB_ORDER_EXPIRY_HOURS_MIN, QAB_ORDER_EXPIRY_HOURS_MAX]. */
export function isQabOrderExpiryHours(value: unknown): boolean;

/**
 * PURE. The ONE place the contradiction is written: delivery offered, flat rate,
 * and no amount to charge. Deliberately shaped so the SAME function answers for
 * a full configuration (every key present) and for a partial payload (a key that
 * is not there is `undefined`, and `undefined === null` is false), which is
 * exactly the border the other side's schema refine can see.
 */
export function isQabPurchaseConfigInconsistent(input: {
  deliveryEnabled?: boolean;
  deliveryFeeMode?: string;
  deliveryFee?: number | null;
}): boolean;

/* -- The field schemas, built ON those predicates. ------------------------- */

/**
 * `number | null`. The `z.unknown().transform()` shape is the repository's
 * (`qabProductPriceSchema`), and it is what keeps the annotation honest under
 * `strict: false`.
 */
export const qabDeliveryFeeSchema: z.ZodType<number, unknown>;

/** `number`. Rejects `null`, a fractional value and anything out of range. */
export const qabOrderExpiryHoursSchema: z.ZodType<number, unknown>;

/** The five, together. STRICT. */
export const qabStorePurchaseConfigSchema = z
  .object({
    checkoutMode: qabCheckoutModeSchema,
    deliveryEnabled: z.boolean(),
    deliveryFee: qabDeliveryFeeSchema,
    deliveryFeeMode: qabDeliveryFeeModeSchema,
    orderExpiryHours: qabOrderExpiryHoursSchema,
  })
  .strict();
export type IQabStorePurchaseConfig = z.infer<typeof qabStorePurchaseConfigSchema>;

/**
 * What changed in ONE operation: only the keys that did, carrying the value they
 * ended up with. A key that did not change is NOT here — not even as
 * `undefined`. See ADR ADRIAN-0152 (b).
 */
export const qabStorePurchaseConfigChangesSchema = qabStorePurchaseConfigSchema.partial();
export type IQabStorePurchaseConfigChanges = z.infer<typeof qabStorePurchaseConfigChangesSchema>;

/** One broken rule, ready for the screen. Same shape as F-005's opening-hours issue. */
export const qabPurchaseConfigIssueSchema = z
  .object({
    code: z.enum(QAB_PURCHASE_CONFIG_ISSUE_CODES),
    field: z.enum(QAB_STORE_PURCHASE_CONFIG_KEYS),
  })
  .strict();
export type IQabPurchaseConfigIssue = z.infer<typeof qabPurchaseConfigIssueSchema>;
```

Semántica exacta de los dos predicados numéricos, para que implementación y test no puedan
discrepar en los bordes:

| Entrada | `isQabDeliveryFee` | `isQabOrderExpiryHours` |
|---------|--------------------|--------------------------|
| `null`, `undefined`, `"12"`, `NaN`, `Infinity` | `false` | `false` |
| `0` | `true` | `false` |
| `1` | `true` | `true` |
| `12.34` | `true` | `false` (no entero) |
| `12.345` | `false` (`hasQabScale(v, QAB_AMOUNT_DECIMALS)`) | `false` |
| `-1` | `false` | `false` |
| `8760` / `8761` | `true` / `true` | `true` / `false` |
| `999999999999.99` | `true` | `false` |
| `10 ** 12` | `false` (tope excluyente) | `false` |

`isQabDeliveryFee` **reutiliza `hasQabScale` de `src/schemas/qabDecimals.ts`**: la regla de los dos
decimales ya está escrita ahí y no se vuelve a escribir (ADR 0047).

## 5. El delta y el constructor del `payload`

### 5.1 `src/lib/qab/qabStorePurchaseConfig.ts` (nuevo)

Capa de servidor: es el único módulo de este feature que conoce `Prisma.Decimal`.

```ts
/** The five columns as read from a Tienda row. Derived, never re-declared. */
export type IQabStorePurchaseConfigRow = Pick<
  ITiendaOnlineLocalRow,
  (typeof QAB_STORE_PURCHASE_CONFIG_KEYS)[number]
>;

/**
 * PURE. The stored amount as a wire number. Returns `null` for `null` AND for
 * `undefined` (`value == null` covers the three reachable shapes, E-079), and
 * accepts a plain number so a caller that already converted is not punished.
 */
export function toQabDeliveryFee(
  value: Prisma.Decimal | number | null,
): number | null;

/**
 * PURE. A row projection -> the five values in wire shape.
 *
 * TOLERANT ON READ, like `toTiendaOnlineLocal` is with a calendar stored before
 * its format existed: a vocabulary value the enum does not contain, or an hour
 * count outside the range, reads as the DEFAULT instead of taking the screen
 * down. A row written by hand with SQL is then corrected by the first save,
 * because the delta will see it as a change.
 */
export function toQabStorePurchaseConfig(
  row: IQabStorePurchaseConfigRow,
): IQabStorePurchaseConfig;

/**
 * PURE. What changed between two PERSISTED states of the same row.
 *
 * Compares the five with `===` over the WIRE shape — never over the row, where
 * two `Prisma.Decimal` are two objects and `===` is always false, which would
 * put `deliveryFee` in every single delta (ADR ADRIAN-0152 (d)).
 *
 * The returned object holds ONLY the keys that changed, with the value from
 * `after`. It never holds a key whose value is `undefined`: the criterion is
 * checked with `Object.keys`, and a present-but-undefined key answers the
 * opposite of what it looks like.
 */
export function collectQabStorePurchaseConfigChanges(
  before: IQabStorePurchaseConfig,
  after: IQabStorePurchaseConfig,
): IQabStorePurchaseConfigChanges;
```

### 5.2 `src/lib/qab/qabStorePayload.ts`

```ts
/**
 * Raised when the payload about to be emitted would be contradictory on its own.
 * Thrown INSIDE the mutation's transaction, so it rolls the write back — the
 * same net `QabStorePayloadError` is for an invalid calendar. Unreachable from
 * the screen, because the PATCH body schema rejects it first; it exists so a
 * future caller cannot reach it either.
 */
export class QabStorePurchaseConfigError extends Error {}
```

`buildQabStorePayload` no cambia de nombre ni de firma pública (sigue tomando un
`IQabStorePayloadInput` y devolviendo un `IQabStorePayload`). Cambia por dentro, y **solo** esto:

1. Antes del `parse`, comprueba
   `isQabPurchaseConfigInconsistent(input.purchaseConfigChanges)`; si es cierto, lanza
   `QabStorePurchaseConfigError`.
2. Esparce el delta sobre el objeto que ya construía, con la misma forma que ya usa `openingHours`
   —una clave que no está **no viaja**, en vez de viajar como `undefined`—:

```ts
    ...input.purchaseConfigChanges,
```

Un delta vacío deja el `payload` **byte a byte igual** al que F-005 emite hoy. Ese es el criterio 4.

### 5.3 `src/lib/tiendaOnline/tiendaOnlineStore.ts`

- `TIENDA_ONLINE_LOCAL_SELECT` gana las cinco columnas. Con eso, la lectura de `existing` dentro de
  la transacción (que ya lo esparce) las trae sin tocar nada más.
- `toTiendaOnlineLocal` proyecta las cinco a la salida de la pantalla, pasando por
  `toQabStorePurchaseConfig(row)` — una sola conversión, la misma que alimenta el delta.
- `saveTiendaOnlineLocal` escribe las cinco en el `data` del `update` y calcula el delta:

```ts
// Inside the transaction, AFTER the update and BEFORE building the payload.
// Both operands are PERSISTED states of the same row, never the request body:
// ADR 0032 stays true, ADR ADRIAN-0152 (a) says why.
const purchaseConfigChanges = collectQabStorePurchaseConfigChanges(
  toQabStorePurchaseConfig(existing),
  toQabStorePurchaseConfig(updated),
);
```

y lo pasa a `buildQabStorePayload({ ..., purchaseConfigChanges })`.

## 6. Contratos de API

| Método | Ruta | Body | Respuesta |
|--------|------|------|-----------|
| `PATCH` | `/api/tienda-online/configuracion/[tiendaId]` | `tiendaOnlineLocalUpdateSchema`: el bloque completo de F-005 **más las cinco claves, las cinco obligatorias** (reemplazo completo, ADR 0032) | `200` `tiendaOnlineLocalUpdateResultSchema` · `400` `{ error: TIENDA_ONLINE_API_ERRORS.invalidBody }` · `400` `{ error, issues }` solo para `horarios` (sin cambios) · `403` · `404` · `500` |
| `GET` | `/api/tienda-online/configuracion` | — | `tiendaOnlineConfiguracionSchema`, con las cinco dentro de cada `local` |

`src/schemas/tiendaOnline.ts`:

```ts
// tiendaOnlineLocalSchema (what the screen reads) gains the five, always present:
    checkoutMode: qabCheckoutModeSchema,
    deliveryEnabled: z.boolean(),
    deliveryFee: qabDeliveryFeeSchema,
    deliveryFeeMode: qabDeliveryFeeModeSchema,
    orderExpiryHours: qabOrderExpiryHoursSchema,

// tiendaOnlineLocalUpdateSchema (the PATCH body) gains the same five, and ONE
// cross-field check at the end. `.strict()` FIRST, then the refinement:
export const tiendaOnlineLocalUpdateSchema = z
  .object({ /* ...the F-005 keys..., plus the five above */ })
  .strict()
  .superRefine((value, ctx) => {
    if (isQabPurchaseConfigInconsistent(value)) {
      ctx.addIssue({ code: "custom", message: "Inconsistent delivery configuration" });
    }
  });
```

Tres decisiones de la ruta, escritas para que no se «arreglen» luego:

1. **La respuesta a un cuerpo inválido en cualquiera de las cinco es el `400` genérico
   (`invalidBody`)**, no un cuerpo con códigos como el de `horarios`. El motivo no es pereza: un
   calendario **guardado** puede ser inválido sin que el comerciante haya escrito nada (la columna
   aceptó cualquier JSON antes de F-005), y por eso aquel necesitaba explicarse desde el servidor.
   Las cinco llegan siempre de controles cerrados y de un formulario que ya las valida (§ 7): quien
   explica el error al comerciante es la pantalla, y llegar a este `400` significa que alguien llamó
   a la API a mano. **El mensaje del `refine` no viaja al navegador** (E-031, E-069).
2. **`onlyOpeningHoursFailed` no se toca.** Una infracción de las cinco produce issues cuyo
   `path[0]` no es `"horarios"` —la del `superRefine` no tiene `path`—, así que cae sola en el `400`
   genérico.
3. **`QabStorePurchaseConfigError` se mapea a ese mismo `400` genérico**, junto a los `catch` que ya
   existen.

`updateTiendaOnlineLocal` (`src/services/tiendaOnlineService.ts`) no cambia de firma: el tipo del
body crece solo.

## 7. La otra superficie del invariante: el formulario

`src/utils/tiendaOnlineDraft.ts` — es el módulo `.ts` donde ya vive la traducción formulario ↔ cable
y es lo único de la pantalla que la suite puede ejercitar (E-015).

```ts
// ITiendaOnlineDraft gains five fields. The two numbers are STRINGS, like every
// other numeric field of this draft: while somebody types "12." there is no
// number yet. The two enums are typed, because they come from a closed control.
  checkoutMode: IQabCheckoutMode;
  deliveryEnabled: boolean;
  deliveryFee: string;
  deliveryFeeMode: IQabDeliveryFeeMode;
  orderExpiryHours: string;
```

- `draftFromLocal`: `deliveryFee` con el helper `numberText` que ya existe (`null` -> `""`);
  `orderExpiryHours` con `String(local.orderExpiryHours)`; las otras tres, directas.
- `draftToUpdate`: `deliveryFee` con el helper `toNullableNumber` que ya existe (vacío -> `null`);
  `orderExpiryHours` con un helper local nuevo, `toNumberOrNaN` (**vacío -> `NaN`**, no `0`, que es
  lo que devolvería `Number("")`); las otras tres, directas.
- **La regla de que un campo oculto no pierde su valor** (spec, § contexto de UI) se cumple sola:
  `draftToUpdate` manda siempre `deliveryFee` y `deliveryFeeMode`, los pinte la pantalla o no.

```ts
/**
 * PURE. Every rule the purchase configuration breaks, in a fixed order, empty
 * when there is none. The form's half of acceptance criteria 6, 7 and 8: the
 * screen calls it BEFORE the save, so a rejected draft never becomes a request.
 */
export function collectPurchaseConfigIssues(
  draft: ITiendaOnlineDraft,
): IQabPurchaseConfigIssue[];
```

Orden y exclusividad, fijados aquí porque un test compara arrays:

1. **`deliveryFee`** (como mucho UNA, en este orden): vacío tras `trim` no es infracción y vale
   «sin importe» · no finito -> `DELIVERY_FEE_NOT_A_NUMBER` · `< 0` -> `DELIVERY_FEE_NEGATIVE` ·
   más de dos decimales -> `DELIVERY_FEE_TOO_MANY_DECIMALS` · `>= QAB_DELIVERY_FEE_MAX_EXCLUSIVE`
   -> `DELIVERY_FEE_TOO_LARGE`. Campo: `"deliveryFee"`.
2. **`orderExpiryHours`** (como mucho UNA): vacío, no finito o fraccionario ->
   `ORDER_EXPIRY_HOURS_NOT_AN_INTEGER` · entero fuera de rango -> `ORDER_EXPIRY_HOURS_OUT_OF_RANGE`.
   Campo: `"orderExpiryHours"`.
3. **La contradicción**, y **solo si `deliveryFee` no produjo ninguna infracción**: si
   `isQabPurchaseConfigInconsistent` es cierto sobre el importe ya interpretado ->
   `DELIVERY_CONFIG_INCONSISTENT`, campo `"deliveryFee"` (que es donde el comerciante actúa para
   arreglarlo).

**Requisito de la pantalla** (`src/app/tienda-online/configuracion/page.tsx`): la función `persist`
—la única puerta al guardado, incluidas las dos llamadas que fuerzan `publicarEnTienda`— llama a
`collectPurchaseConfigIssues` y **sale antes de `save(...)`** si devuelve algo. Criterios 6 y 8 se
verifican comprobando que no aparece fila nueva en `OutboxEvento`, así que no basta con deshabilitar
el botón: la guarda va dentro de `persist`.

El **copy** de cada código y la disposición de los controles son del contrato de diseño
(`.agents/designs/F-016.md`). Si ese contrato necesita un símbolo puro nuevo, **vuelve al
arquitecto para añadirlo aquí** antes del paso 5 (E-035): el `dev-tester` solo puede probar lo que
esta § 10 enumera.

## 8. Outbox: `STORE_DELIVERY_CONFIG_INCONSISTENT` (criterio 7)

**Verificado contra el código: no hay que cambiar nada, y el criterio ya se cumple.** Queda escrito
para que nadie lo «implemente» otra vez:

- `QAB_OUTBOX_PERMANENT_ERROR_CODES` y `QAB_STORE_SYNC_CODES` ya contienen el código (F-005 lo dejó
  anticipado).
- `planOutboxAck` (`src/lib/qab/outboxAck.ts`) mete la entrada de `failed[]` en `failedAcks`: el
  código **no** está en `QAB_OUTBOX_DEFERRED_ERROR_CODES` —que solo tiene
  `DEPENDENCY_FAILED_IN_BATCH`—, así que no es un aplazamiento.
- `outboxDrain` escribe para esa fila `intentos: { increment: 1 }` y `ultimoError`, y **no escribe
  `procesadoAt`**: solo lo escribe para `processedIds`. El evento sigue pendiente de reintento, que
  es literalmente lo que pide el criterio.
- `collectQabPermanentFailures` lo reporta en `permanentFailures`, y `normalizeOutboxErrorCode` lo
  traduce al código que la pantalla ya enseña (`FAILED`, o `BLOCKED` al agotar los intentos).

**Alcanzabilidad, para que nadie escriba un test imposible:** cuadrecaja **no puede producir** por
sí misma el `payload` contradictorio —lo rechazan el `superRefine` del body y la red de
`buildQabStorePayload`—, así que la rama del `207` se prueba **sembrando la fila en QAB** y enviando
por `curl`, tal como redacta la verificación del criterio. No se escribe un test de unidad que
espere que nuestro constructor emita esa combinación.

`src/schemas/` (importables desde el navegador, sin Prisma); lo que toca la fila y el `payload`, en
`src/lib/qab/` y `src/lib/tiendaOnline/`; la traducción formulario ↔ cable en `src/utils/`; la
pantalla en `src/app/tienda-online/configuracion/` y `src/components/tiendaOnline/`. Ningún
componente importa Prisma. Alias `@/` siempre.

**Aislamiento multi-tenant.** No hay ruta de acceso nueva: el `PATCH` sigue tomando `negocioId`
**solo de la sesión** (`session.user.negocio.id`), la lectura es `findFirst({ where: { id, negocioId } })`
y la escritura `update({ where: { id: tiendaId, negocioId } })` — `Tienda` no tiene
`@@unique([id, negocioId])`, así que el filtro va en el `where`, nunca en un `if` posterior. El
encolado hereda ese mismo `negocioId` y el `payload` toma `businessId` de ahí, jamás del body. Las
cinco columnas no participan en ninguna clave, índice ni filtro, y el delta compara dos proyecciones
que la transacción ya tenía: **cero consultas nuevas**, sin N+1 y sin nada que crezca con el
histórico. El permiso sigue siendo `TIENDA_ONLINE_PERMISOS.configuracionAcceder`, comprobado en el
backend antes de leer el cuerpo: no se añade permiso nuevo. Por eso este feature **no** necesita
informe de `security-guardian`.

**Extensibilidad (F-042), como nota, no como valor emitido.** Añadir `ZONE_BASED` será una línea en
`QAB_DELIVERY_FEE_MODES` y una opción más en la pantalla: la columna es `String` y el vocabulario
vive en una constante, así que no hay migración, ni `ALTER TYPE`, ni cambio de firma aquí. Lo que sí
tendrá que decidir F-042 es qué le pasa al importe y al aviso de «pasar a `ZONE_BASED` apaga el
domicilio en el acto». **En este feature no se escribe ese valor en ningún sitio.**

**Vecindario que hay que tener presente** (regla 4 del spec): un `openingHours` inválido tumba el
evento `STORE` **entero**, así que un guardado que cambie una de las cinco junto a un calendario
inválido no aplica ninguna de las dos cosas. F-005 ya lo valida antes de encolar y aquí no se
reabre.
