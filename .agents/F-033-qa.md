### 10.1 BLOQUEANTE CRÍTICO — el detalle de un deudor con ≥2 movimientos se cae con un 500

**Cómo lo encontré.** Al sembrar el criterio 52 (que necesita dos movimientos en una misma cuenta:
uno de un usuario con nombre y otro con `usuarioId: null`) y abrir la página de detalle en el
navegador, la pantalla completa cayó en el `ErrorBoundaryHandler` genérico («Algo salió mal»), no
en un fallo del criterio. Consola del navegador:

```
TypeError: b.fecha.getTime is not a function
    at .../src_d484214d._.js:5839:30
    at Array.sort (<anonymous>)
    at buildMovimientoRows (.../src_d484214d._.js:5838:10)
    at DeudorDetallePage.useMemo[movimientos] (.../src_d484214d._.js:8927:221)
```

**Causa raíz, verificada leyendo y confirmada ejecutando.**
`src/lib/cuentasPorCobrar/panel.ts:329-333`:

```ts
rows.sort((a, b) => {
  const diff = b.fecha.getTime() - a.fecha.getTime();
  ...
});
```

`buildMovimientoRows` espera `Date` (así lo tipa `IMovimientoRow`), pero
`src/services/cuentasPorCobrarService.ts` (`fetchDeudorDetalle`, línea ~48) devuelve
`response.data` **crudo** — nunca lo pasa por `deudorDetalleResponseSchema.parse(...)`, que es el
único punto que coercería `fecha` de cadena JSON a `Date` (`z.coerce.date()`). En el runtime,
`movimiento.fecha` es un `string` ISO, no un `Date`, y `.getTime()` no existe en un `string`.

**Por qué no se vio antes y por qué es grave.** `Array.prototype.sort` **no invoca el comparador**
cuando el array tiene 0 o 1 elementos — así que toda cuenta con **un único movimiento** (todas las
que usé en mi primera pasada y todas las que sembró el `dev-tester` para sus fixtures unitarios,
que son objetos `Date` de verdad, no JSON) esconden el fallo. En cuanto una cuenta tiene **dos
movimientos** — el caso más ordinario del feature: un segundo abono parcial, o revertir el
primero — la pantalla entera del detalle se cae.

**Reproducido dos veces, de forma independiente, para descartar que fuera un artefacto de mi
siembra:**
1. Con los dos movimientos sembrados para el criterio 52 (uno vía API con la sesión de `Maria
   Cajera`, otro insertado directo por Prisma con `usuarioId: null`, que es la única forma de
   producir un autor nulo ya que la API siempre toma el usuario de la sesión).
2. **Con dos abonos registrados en caliente por la API real, sin ningún truco de siembra** — el
   mismo POST `/abono` que usa cualquier cajero, llamado dos veces sobre la misma cuenta. Mismo
   error exacto.

La API en sí **no tiene el bug**: `GET /api/cuentas-por-cobrar/cliente/{clienteId}` para la cuenta
de la reproducción 1 devuelve JSON perfecto, con `usuarioNombre: "Maria Cajera"` en un movimiento y
`usuarioNombre: null` en el otro — los datos que el criterio 52 pide están ahí. El fallo es
enteramente de la capa cliente (el servicio no valida/coacciona con el schema antes de que
`buildMovimientoRows` reciba los datos).

un solo movimiento, así que también está expuesto).
